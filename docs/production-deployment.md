# Production deployment

English | [中文](production-deployment_CN.md)

## Scope and status

This guide provides a public, release-neutral template for running CLIProxyAPI behind Nginx and, optionally, Cloudflare.
It describes proxy behavior and validation methods; it does not guarantee that every release has the same
application-level request timeout or streaming heartbeat behavior

Check the `config.example.yaml`, release notes, and client behavior for the version you deploy. Test the complete path
before changing production traffic

## Reference topology

```text
Client
  -> Cloudflare (optional)
  -> Nginx and TLS termination
  -> CLIProxyAPI at 127.0.0.1:8317
  -> Upstream provider
```

A timeout can be generated by the client, Cloudflare, Nginx, CLIProxyAPI, or the upstream provider. Record an identifier
and timing at each layer before assigning a status code to one component

## Prerequisites

- Terminate public TLS with a certificate trusted by clients
- When using a Cloudflare Origin CA certificate on Nginx, keep the DNS record proxied; direct clients do not normally
  trust Origin CA certificates, and DNS-only access requires a publicly trusted origin certificate
- Bind CLIProxyAPI to loopback or a private interface when Nginx is the public entry point
- Configure trusted proxy ranges from the `config.example.yaml` shipped with the deployed release
- Require API authentication and keep remote management disabled unless it has a separate access policy
- Select request-size and timeout values from measured traffic, available memory, connection limits, and the longest
  accepted operation
- Save the active Nginx and Cloudflare configuration before changing either layer
- Keep a direct health check that does not expose authenticated API or management routes publicly

## Nginx exact-path template

Place the following locations inside the existing TLS `server` block. The timeout and body-size values are examples;
adjust them without exceeding the application limit or the capacity of the host

```nginx
location = /v1/messages {
    proxy_pass http://127.0.0.1:8317;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    client_max_body_size 32m;
    client_body_timeout 120s;
    proxy_connect_timeout 10s;
    proxy_send_timeout 120s;
    proxy_read_timeout 300s;
    send_timeout 120s;

    proxy_request_buffering off;
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    add_header X-Accel-Buffering no always;
}

location = /v1/responses {
    proxy_pass http://127.0.0.1:8317;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    client_max_body_size 32m;
    client_body_timeout 120s;
    proxy_connect_timeout 10s;
    proxy_send_timeout 120s;
    proxy_read_timeout 300s;
    send_timeout 120s;

    proxy_request_buffering off;
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    add_header X-Accel-Buffering no always;
}
```

Use exact locations so the streaming policy does not silently affect management routes or unrelated endpoints. If a
client uses another documented alias, add that path explicitly after testing it

CLIProxyAPI's SSE handlers send `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, and
`X-Accel-Buffering: no`. HTTP/1.x responses also send `Connection: keep-alive`; HTTP/2 responses do not send the
connection-specific header. These application headers do not replace the Origin settings above. Keep
`proxy_buffering off`, `proxy_cache off`, `gzip off`, and a `proxy_read_timeout` longer than the expected interval
between response bytes at every Nginx layer on the public route

### Timing log

Define `log_format` in the Nginx `http` context, then enable the log in the API `server` or exact locations:

```nginx
log_format cli_proxy_timing escape=json
    '{"time":"$time_iso8601",'
    '"request_id":"$request_id",'
    '"cf_ray":"$http_cf_ray",'
    '"method":"$request_method",'
    '"uri":"$uri",'
    '"status":$status,'
    '"request_length":$request_length,'
    '"body_bytes_sent":$body_bytes_sent,'
    '"request_time":$request_time,'
    '"upstream_status":"$upstream_status",'
    '"upstream_connect_time":"$upstream_connect_time",'
    '"upstream_header_time":"$upstream_header_time",'
    '"upstream_response_time":"$upstream_response_time"}';

access_log /var/log/nginx/cli-proxy-api-timing.log cli_proxy_timing;
```

The example records path and timing without query parameters. Do not add the request body, `Authorization`, cookies, API
keys, or query strings to this log

## Buffering and timeout semantics

| Layer or directive             | What it controls                                                                 | Important boundary                                                                           |
|--------------------------------|----------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| `client_body_timeout`          | Idle time between successive reads of the request body from the client           | Nginx returns 408 when the interval expires; it is not the total upload duration             |
| `proxy_send_timeout`           | Idle time between successive writes while Nginx sends the request to CLIProxyAPI | It is not the total request duration                                                         |
| `proxy_read_timeout`           | Idle time between successive reads of the response from CLIProxyAPI              | Streaming data or heartbeats must arrive before this interval                                |
| `send_timeout`                 | Idle time between successive writes from Nginx to the client                     | A slow or disconnected client can close the downstream path                                  |
| Cloudflare Proxy Read Timeout  | Time allowed for origin response progress                                        | The documented default is 125 seconds and is configurable only for eligible Enterprise zones |
| Cloudflare Proxy Write Timeout | Time allowed while Cloudflare writes the request to the origin                   | The documented limit is 30 seconds and is not configurable                                   |

`proxy_request_buffering off` lets Nginx pass the request body to CLIProxyAPI as Nginx receives it.
`proxy_buffering off` lets Nginx pass response chunks to the client without accumulating the full response.
`proxy_cache off` prevents the proxy cache from handling these API responses. `gzip off` prevents compression from
collecting small heartbeat frames before forwarding them

Longer proxy timeouts do not replace request-size limits, authentication, connection or rate limits, capacity planning,
and client cancellation handling

## Cloudflare Configuration Rule

The DNS record must be proxied by Cloudflare for a Configuration Rule to apply

Create a Configuration Rule with an exact host, method, and path expression. Replace the example host with the public
API host:

```text
(http.host eq "api.example.com" and http.request.method eq "POST" and (http.request.uri.path eq "/v1/messages" or http.request.uri.path eq "/v1/responses"))
```

Set one action only:

```text
Request Body Buffering = Full
```

Do not set Response Body Buffering in the same rule. Do not attach cache, origin, route, or unrelated timeout changes to
this rule

Cloudflare documents `Full` as buffering the complete request body before sending the request to the origin. This can
separate a slow client upload from the Cloudflare-to-Nginx request phase. Nginx can still use
`proxy_request_buffering off` for the next hop, so the two settings do not conflict

`Full` does not increase Cloudflare's 125-second Proxy Read Timeout or 30-second Proxy Write Timeout and does not
guarantee that every 524 will disappear. `None` streams the body directly to the origin without inspection and can
reduce the effectiveness of WAF or other features that require body inspection. Full buffering also does not guarantee
that security products inspect every byte; inspection limits remain plan and product specific

Rules evaluate the URI path without the query string. The expression above intentionally excludes `/v1/messages/`, child
paths, other hosts, GET requests, and endpoint aliases

## Verification

### Configuration

1. Run `nginx -t` before every reload
2. Reload Nginx gracefully and confirm the old worker exits
3. Confirm both exact paths reach CLIProxyAPI through the public hostname
4. Confirm management routes and other hosts do not inherit the streaming locations
5. In Cloudflare, confirm the rule matches only the intended proxied host and two POST paths, and that its only action
   is Request Body Buffering `Full`

### Slow request body

Use generated data with no credentials or user content. The following files are slightly larger than 1 MiB and take more
than two minutes each at 8 KiB/s:

```bash
python3 - <<'PY'
import json

padding = "x" * (1024 * 1024)
with open("/tmp/cpa-messages.json", "w", encoding="utf-8") as output:
    json.dump({
        "model": "test-model",
        "stream": True,
        "max_tokens": 1,
        "messages": [{"role": "user", "content": padding}],
    }, output)
with open("/tmp/cpa-responses.json", "w", encoding="utf-8") as output:
    json.dump({
        "model": "test-model",
        "stream": True,
        "input": padding,
    }, output)
PY

for endpoint in messages responses; do
    curl --http1.1 --limit-rate 8k --max-time 240 \
        -H 'Content-Type: application/json' \
        --data-binary "@/tmp/cpa-${endpoint}.json" \
        -o /dev/null \
        -w "endpoint=${endpoint} status=%{http_code} total=%{time_total}s upload=%{size_upload}\n" \
        "https://api.example.com/v1/${endpoint}"
done
```

Without an API key, a 401 after the body is received is an acceptable origin result. The check is invalid if Cloudflare
blocks the request before the origin. Correlate the response's `CF-Ray: <CF-RAY>` value with the timing log and compare
client upload time, Nginx `request_time`, upstream header time, and response bytes

A successful synthetic request proves only the tested route and conditions. It does not prove that every real client,
request size, protocol, or provider path is fixed

Repeat the test with the protocol and client stack used in production. The command above fixes HTTP/1.1 only to provide
one reproducible baseline

### Streaming

Use a local delay stub or a dedicated test provider instead of delaying a paid production request. For each supported
release and client, verify:

- response status, `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, and
  `X-Accel-Buffering: no` at the Origin and public hostname
- no `Connection` response header over HTTP/2
- first byte and first semantic event timing
- heartbeat arrival before upstream setup completes, before the first semantic event, and during an ordinary response gap
- multiple response events and exactly one terminal event
- prompt connection shutdown after the terminal event, including when the upstream transport does not close normally
- non-streaming JSON responses
- client cancellation and the resulting Nginx status

## Troubleshooting

| Status | Meaning in this topology                                                      | What to check                                                                                                                    |
|--------|-------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|
| 408    | A layer stopped waiting for request headers or body data                      | Identify which layer generated it; compare client upload gaps, Nginx `client_body_timeout`, and the deployed application release |
| 499    | Nginx observed the client closing the connection                              | Check the client's timeout or retry first; 499 is often the result of an earlier delay                                           |
| 504    | A gateway timed out while waiting for an upstream                             | Compare Nginx proxy timing with CLIProxyAPI and provider timing                                                                  |
| 524    | Cloudflare connected to the origin but its origin read or write limit expired | Compare the Cloudflare ray with Nginx timing; Full buffering affects one request-body path but not every 524 cause               |

When a client retries, group attempts by a redacted request identifier and compare request size, start time, status,
response bytes, and retry count. Do not assume consecutive requests represent separate user actions

## Security and redaction

- Keep API and management authentication enabled
- Trust forwarded headers only from known proxy addresses
- Apply connection and rate limits that match the accepted timeout window
- Keep a finite request-body limit and enough temporary storage for proxy buffering
- Do not log request or response bodies, credentials, cookies, query tokens, or complete header maps
- Redact public host names, origin IP addresses, rule IDs, Cloudflare rays, process IDs, local paths, hashes,
  timestamps, traffic counts, and session identifiers before publishing diagnostics
- Use placeholders such as `api.example.com`, `<CF-RAY>`, and `<REDACTED>` in issues and documentation

## Limitations

- The templates cover only `/v1/messages` and `/v1/responses`
- Other endpoint aliases require separate, explicit rules
- Client, operating-system, corporate proxy, provider, and application timeouts can still end the request
- Cloudflare limits and feature availability depend on the active plan and current product documentation
- Buffering changes request timing and cancellation behavior; test streaming and non-streaming clients separately
- The guide does not claim that all 408, 499, 504, 524, or client retries share one cause

## Rollback

1. Disable the single Cloudflare Configuration Rule and confirm the effective request body mode returns to its previous
   value
2. Restore the previous Nginx configuration, run `nginx -t`, and reload gracefully
3. Roll back one layer at a time, then repeat the same request and timing checks
4. Do not expose the loopback CLIProxyAPI listener publicly as a temporary bypass
